# Engineering Case Study — Creator Decision Intelligence

이 문서는 포트폴리오를 위한 **문제 → 가설 → 구현 선택 → 실제 장애 → 교훈** 기록입니다. 프로젝트가 상용 제품처럼 보이도록 성과를 과장하지 않고, 실제 구현과 운영 중 발견한 한계를 구분합니다.

## 1. 제품 문제: 다음 주제 하나를 정하는 데 필요한 반복 노동

한국어권 영어교육 채널을 직접 운영하면서 영상 한 편을 기획하기 위해 경쟁 영상 검색, 채널별 성과 비교, 댓글/자막 분석, 기존 강의 중복 확인, 설명 구조 설계까지 반복해야 했습니다. 초기 목표는 '대본을 AI가 작성한다'가 아니라 **어떤 주제를, 왜 지금 제작해야 하는가**를 근거로 결정하는 것이었습니다.

**접근:** 시장 데이터와 채널의 과거 콘텐츠를 결합하고, AI가 제시한 추천을 사람의 최종 선택으로 연결하는 워크플로를 만들었습니다.

## 2. 단순 조회수 추천의 실패

**관찰:** 초기 검색 결과는 100문장·쉐도잉·반복 재생형 영상처럼 절대 조회수가 높은 콘텐츠에 편중됐습니다.

**원인 가설:** 채널의 기본 규모가 크면 콘텐츠의 고유한 성과가 아닌 채널 효과가 점수를 지배합니다.

**변경:** 채널별 과거 누적 조회수 중앙값 대비 후보 영상의 성과(Channel Outlier), 구독자 대비 조회, 최근 업로드 경과시간, 표본 수를 분리해서 평가했습니다.

**남은 한계:** 과거 시점별 조회수 스냅샷을 확보하지 못하면 누적 조회수 비교는 retrospective approximation입니다. 표본 수가 적을 때는 강한 결론을 내리지 않습니다.

## 3. 시장 인기는 있는데 왜 내 채널의 기회가 아닐까?

**관찰:** 시장에 비어 보이는 '병원영어' 등의 주제가 과도하게 추천된 사례가 있었습니다. 실제 자료에는 오래된 영상, 기준 표본이 적은 채널, 조회수가 극히 낮은 최근 업로드가 섞여 있었습니다.

**교훈:** '내 채널에 없다'와 '시장 수요가 있다'는 서로 다른 조건입니다.

**변경:** Knowledge Gap을 계산하기 전에 Market Evidence Gate와 표본 신뢰도를 따로 검토했습니다. 콘텐츠의 종류(강의·훈련)와 비즈니스 역할(신규 유입·신뢰 형성)도 분리했습니다.

**남은 한계:** 관측 영상으로 시장 전체 수요를 확정할 수 없고, 추천 성과 역시 업로드 후 관찰이 필요합니다.

## 4. 검색 결과는 있었는데 정작 영상 내용이 없었다

**관찰:** Transcript 확보 실패 상태에서도 메타데이터/댓글 기반으로 심층 조사와 대본 생성이 진행되는 설계 문제가 있었습니다.

**왜 중요한가:** 이 프로젝트의 차별점은 각 영상이 *무엇을 가르치고 어떻게 설명하는지*를 분해하는 데 있습니다. 제목·조회수만으로는 설명 방식에 관한 강한 주장을 뒷받침할 수 없습니다.

**변경:** Transcript Coverage Gate, Explanation Atom, Content DNA 분석, 채널 대본과 Hybrid RAG(BM25 + embeddings + RRF)를 분리했습니다. 자막이 부족하면 Deep Research를 정상 완료한 것으로 표시하지 않습니다.

**남은 한계:** 영상마다 공개 자막 여부가 다르며, 일부 환경에서 IP 차단과 접근 제한이 발생합니다.

## 5. 클라우드 자막 수집에서 로컬 실행으로

**증상:** 클라우드/Colab 환경에서 자막 요청이 차단됐고, 버전 업데이트로 캐시가 소실되자 재수집 요청이 반복됐습니다.

**변경:** Windows 로컬 실행 및 디스크 캐시를 도입하고 Program Versions와 Persistent Data를 분리했습니다. 재실행 때 기존 transcripts/comments/LLM 캐시를 우선 재사용하도록 설계했습니다.

**남은 한계:** 캐시가 없고 외부 API가 차단된 상황에서 원격 영상에 접근할 수 있다고 보장하지 않습니다.

## 6. 두 개의 추천 엔진 비교: A와 Hermes B

**목표:** 기존 채널·시장 데이터 기반 추천 A와 별도 웹 조사 기반 Hermes B를 함께 비교하여, 한 방식의 편향에 전적으로 의존하지 않기.

**실제 장애:** Hermes의 구조화된 응답이 기대한 `strategy_route` 값을 빠뜨리거나, 추천 후보에 연결된 조사 URL이 검사 규칙을 통과하지 않아 추천 전체가 중단됐습니다.

**변경:** 허용된 전략 경로 표기 정규화, 누락 항목 재확인, 동일 영상 URL 정규화, 근거 URL 매칭 및 조사 진단 로그를 추가했습니다.

**중요한 한계:** 링크의 존재가 그 주제의 수요/성과를 증명하지 않습니다. A/B는 **두 조사 워크플로 비교**이지 동등 조건 성능 평가가 아닙니다.

## 7. 실제 운영 비용과 장애

- **YouTube Data API:** 검색 쿼터 부족으로 신규 수집이 중단됐습니다. 기존 ID와 근거 캐시 재사용 전략이 필요합니다.
- **OpenAI API:** 429 `insufficient_quota`로 자막 분석 중단을 경험했습니다. ChatGPT 구독과 API 크레딧은 별개입니다.
- **추천 근거 일치:** '연결된 경쟁 영상 0개'와 심층 조사 Transcript 100%가 동시에 표시되는 혼란을 발견했습니다. 두 수치는 서로 다른 단계의 지표였으며, UI 문맥을 명확하게 분리해야 합니다.
- **분석 그래프:** 그래프 축의 음수 표시가 실제 음수 조회수처럼 오해될 수 있어 표현 검토가 필요했습니다.

이 문제들은 해결을 시도하거나 일부 보완했으나, **모든 환경에서 재현 테스트로 완전히 해소된 상태라고 주장하지 않습니다.**

## 8. 대본 작성의 품질 기준

초기 Draft A는 구조화된 초안을 제공했지만, 후반부가 댓글 요청으로 끝나고 강의의 핵심 약속을 회수하지 못하는 문제가 있었습니다.

**변경:** Critic이 정확성·설명 난이도·인지 보상·과도한 모방·결말 완결성을 검사하도록 설계했습니다. Draft B는 Draft A를 무조건 다시 쓰는 대신 확인된 문제를 선택적으로 개선하는 방향입니다.

해외/국내 교육 채널 벤치마크에서는 주제와 설명 원리만 참고하고 특정 대본·독특한 예시·연출을 그대로 복제하지 않습니다.

## 9. UX 리디자인: '데이터가 많다'와 '좋은 제품'은 다르다

**문제:** 내부 진단 값과 근거가 전면에 쌓이면서 사용자가 정작 제작할 주제를 결정하기 어려웠습니다. 초기 UI 개편에서는 오히려 불필요한 색상과 설명이 늘어났습니다.

**변경:** 검정·회색 기반의 입력 중심 UI, 신규 유입/신뢰 형성 선택, 결과·다음 행동 우선, 모든 상세 근거를 하단 단일 펼침 영역으로 모으는 디자인을 적용했습니다.

**지향:** 사용자가 조작법보다 주제 결정에 집중하는 제품.

## 10. 무엇을 검증했고 무엇은 아직 검증하지 못했나?

- 실제 로컬 환경에서 주제 추천, 심층 조사, Draft A까지 진행한 사례가 있습니다.
- 자동화/모의 테스트를 수행했으나 Windows·Docker·유료 외부 API를 모두 포함한 종단 간 안정성은 별도 검증 대상입니다.
- 추천을 사용한 뒤 유튜브 조회수가 상승했다는 인과효과는 입증하지 않았습니다.
- 7일/28일 관측 데이터를 장기적으로 누적해 추천 품질을 평가하는 것이 후속 목표입니다.
