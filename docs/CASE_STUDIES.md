# Engineering Case Studies
### Creator Decision Intelligence — Problems, Root Causes & Trade-offs

이 문서는 프로젝트 개발 중 **실제로 관측한 실패와 설계 변경**을 기술한다. 각 사례는 **관측 → 원인 가설/확인 근거 → 수정 → 남은 한계**로 구분한다. 사용자가 보고한 Windows 실행 오류와 현재 로컬 코드의 함수 구현을 함께 근거로 작성했으며, 실제 생산 환경에서 효과가 정량 검증된 것처럼 주장하지 않는다.

---

## Case 01 · 인기 영상만 찾으면 좋은 주제를 놓친다

**관측.** 초기 추천에서는 절대 조회수가 높은 '100문장', '쉐도잉', '여행영어' 같은 반복형 콘텐츠가 과도하게 선정됐다. 반대로 구독자 수가 작은 채널에서 새 영상이 급격히 성장하는 신호는 구독자 수 하한선 때문에 누락될 수 있었다.

**원인.** '큰 채널이라 조회수가 많은 것'과 '같은 채널의 평소 성과보다 이례적으로 잘된 것'을 분리하지 않은 추천 기준이었다.

**설계 변화.**
- Absolute Views, Subscriber Breakout, Channel Outlier, Recent Breakout을 독립 신호로 다룬다.
- Channel Outlier ≈ 해당 영상의 현재 누적 조회수 / 같은 채널 비교 영상의 현재 누적 조회수 중앙값.
- 과거 조회수 시점별 스냅샷을 갖지 않는 경우, 이것은 **retrospective approximation**이며 같은 업로드 경과 시간의 엄밀한 비교는 아니다.
- baseline 표본이 너무 작으면 강한 증거가 아니라 '표본 부족'으로 본다.
- 추천에서 최근 급상승과 반복 수요 신호의 다양성을 고려하지만, 근거가 없는 후보를 강제로 3개 채우지 않는다.

**한계.** 조회수와 제목 신호만으로 시청자의 실제 학습 효과나 미래 영상 성과를 예측할 수 없다.

**관련 코드:** `topic_ranking.py`, `topic_quality.py`, `yra_tools/youtube_tools.py`.

## Case 02 · 자막 0개인데 심층 조사와 대본이 생성됐다

**관측.** 초기 버전은 Transcript가 확보되지 않아도 영상 제목·댓글·메타데이터를 사용해 Draft까지 진행하는 경로가 있었다. 개발자는 화면상 '심층 조사 완료'가 나타나는 것을 발견했지만 실제 학습 내용을 읽은 증거가 없었다. 일부 클라우드 환경에서는 YouTube Transcript 접근이 차단됐고, 로컬로 이동한 뒤에도 캐시를 잃으면 재요청으로 차단 위험이 커졌다.

**원인.** 장애 복구용 fallback을 정상적인 심층 조사 입력으로 취급했다. 배포 버전과 사용자 캐시가 동일한 폴더에 있으면 새 ZIP 적용 과정에서 캐시도 지워질 수 있었다.

**설계 변화.**
- 시장 후보 수와 Transcript 성공 수를 따로 기록하고 Coverage를 계산한다.
- 확보율이 충분하지 않은 경우 실제 Deep Research를 중단한다. 예비 아이디어 제시와 최종 대본 출력을 구분한다.
- `youtube_consultant_data/cache` 등 지속 데이터는 실행 코드 버전과 분리한다.
- Transcript 성공과 실패 사유를 구분해 표시하고, 성공한 캐시를 다시 사용한다.

**한계.** YouTube 자막 제공 여부, IP 제한, 동영상별 접근 설정은 프로그램이 완전히 통제할 수 없다. 100% 확보율도 후보 4개만 수집했을 때와 40개를 수집했을 때 통계적 의미가 다르다.

**관련 코드:** `pipeline.py::_transcript_coverage`, `cache.py`, `transcript_fallback.py`.

## Case 03 · Hermes 전략 경로 문자열 하나가 전체 추천을 막았다

**관측.** 로컬 오류: `Hermes 주제 2의 전략 경로가 없거나 유효하지 않습니다.`

**원인.** 결과 스키마에 허용된 전략 경로가 `승자 심화`, `인접 확장`, `신규 실험`으로 제한되어 있었고, 모델 응답의 누락 또는 표기 차이도 통과하지 못했다.

**수정.** `normalize_strategy_route()`에서 허용 범위 내의 표기 차이만 정규화하고, `repair_invalid_topic_routes()`에서 전략 경로에 한해 제한된 재요청을 수행하도록 했다. **제목·순위·출처는 수정하지 않는 정책**을 유지했다.

**한계.** 실제로 어떤 전략이 맞는지 판단 불가능한 응답은 임의로 보완하지 않고 실패 처리한다. '오류가 안 난다'는 것과 '판단이 정확하다'는 것은 다르다.

**관련 코드:** `topic_experiment.py`.

## Case 04 · 조사 URL은 있는데 추천과 연결되지 않았다

**관측.** 로컬 오류: `Hermes 후보 3개 모두 조사 링크와 연결되지 않아 B 추천을 확정할 수 없습니다.`

**원인.** Hermes가 반환한 추천의 참고 링크와 웹 도구가 실제 열람해 확인한 링크의 연결이 불완전했다. URL 표기 차이와 추가 조사 이후 인용 재생성이 진단 대상이었다.

**수정.**
- 출처 링크의 허용 여부와 관측 출처를 점검한다.
- 동일한 영상을 가리키는 URL 표기 차이의 비교를 개선한다.
- 후속 조사 시 기존 주제·순위를 보존하고 링크만 재검토한다.
- 근거가 없으면 성공한 것으로 조작하지 않고, 제외한 링크와 남은 불확실성을 기록한다.

**한계.** 유효한 링크 확보는 **주제의 시장 수요, 전환율, 조회수 성과의 증명과 다르다.** 실제 관련성이 부족한 링크를 숫자 채우기 용도로 쓰지 않는다.

**관련 코드:** `topic_experiment.py`, `topic_quality.py`, `hermes_integration/adapter.py`.

## Case 05 · 429 하나에도 서로 다른 장애가 있다

**관측 A.** 시장 Transcript를 확보한 뒤 LLM 분석 단계에서 `429 insufficient_quota / credit_balance_exhausted` 오류가 발생했다.

**관측 B.** 별개 실행에서는 `YouTube 검색 할당량이 부족합니다.`가 표시됐다.

**원인.** OpenAI API의 사용 크레딧과 YouTube Data API의 일일 검색 quota는 서로 다른 서비스의 제한이다. 각각의 실패를 같은 'AI 오류'로 처리하면 문제 해결 행동이 잘못된다.

**대응.**
- OpenAI 크레딧 오류: API 결제·사용 한도를 확인하고, 가능한 경우 완료된 영상 분석 캐시를 재활용한다.
- YouTube 검색 quota: 불필요한 새 검색을 줄이고 이미 관측한 영상 ID 및 시장 근거를 우선 활용한다.
- 실패 사실을 숨기지 않으며, 실제로 확보한 데이터와 미확인 데이터를 구분한다.

**한계.** 캐시를 이용해도 관측 데이터가 새로워지지는 않는다. 비싼 검색을 줄이는 것과 올바른 최신 시장 정보를 얻는 것은 트레이드오프다.

**관련 코드:** `research_resilience.py`, `pipeline.py`, `cache.py`.

## Case 06 · 수집률 100%와 관련 영상 0개가 함께 표시됐다

**관측.** 한 사용 흐름에서 `시장 후보 4개 · Transcript 4개 (100%)`가 표시되는 동시에 `연결된 경쟁 영상 0개 / 전체 조사 표본 16개`가 출력됐다.

**원인 분석.** 화면에 표시된 두 수치는 서로 다른 단계의 모집단이었다. 전자는 **선택한 주제의 후속 조사 후보**였고, 후자는 **이전 A/B 비교 단계에서 제목 키워드 기반 연결**이었다. 동일한 '시장 근거'처럼 보이게 한 라벨이 사용자에게 잘못된 인상을 줬다.

**배운 점.** 수집 커버리지, 추천과 링크의 연결 정도, 실제 시청자 수요는 별개의 지표다. 화면에는 지표별 분모·단계·의미를 설명해야 한다.

**미완료:** 실제 추천 정밀도 개선과 지표 의미의 UI 통합은 추가 개선 여지가 있다.

**관련 코드:** `research_resilience.py::source_video_ids`, `pipeline.py`, UI presenter.

## Case 07 · 기능이 많아질수록 제품이 복잡해졌다

**관측.** A/B 추천, 수요 제한, 검색 상태, 그래프, 경고, 댓글, 상세 판단 근거가 한 화면에 동시에 표시되어 핵심 행동인 **'그래서 어떤 주제를 선택하지?'**가 흐려졌다. Draft B가 기술적으로 존재했지만 접힌 보조 메뉴에 들어가 사용자에게 보이지 않았다.

**원인.** 개발자 검증용 관측 자료와 실제 제작자의 의사결정 화면을 충분히 분리하지 않았다.

**UI 원칙 변경.**
- 첫 화면: **내 채널에 맞는 다음 주제 찾기** / 신규 유입·신뢰 형성 / 채팅 입력.
- 각 단계: 선택지와 가장 중요한 **다음 행동 버튼 하나**.
- 조사 통계·근거·오류 로그: 하단 `판단 근거 · 데이터 보기`로 이동. 단, API 장애 등 즉시 행동이 필요한 오류는 바로 알린다.
- Draft A/B 최종 선택과 원고 확정은 명시적인 종료 경험으로 만든다.

**한계.** UI 간소화는 근거 자체를 숨기면 안 된다. 중요한 불확실성은 상세 패널 안에만 묻히지 않도록 설계해야 한다.
